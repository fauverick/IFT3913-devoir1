# Evaluation Report: ChatUniTest in Apache Tika

This report documents our empirical findings and workflow observations when using **ChatUniTest** to generate unit tests within the Apache Tika project (`tika-parser-pdf-module`).

---

## 1. Where are the Tests Generated?

When executing ChatUniTest goals (e.g., `mvn chatunitest:method` or `mvn chatunitest:class`), the generation outputs are structured across two locations:

### A. Intermediate Logs and Working Files
* **Path:** `/tmp/chatunitest-info/`
* **Contents:**
  * Raw prompt history and token metrics.
  * Intermediate compiler error messages (e.g., `*CompilationError_*.txt`).
  * Attempt mappings and iteration logs per class and method.

### B. Generated Test Files
* **Path:** `<module-path>/chatunitest-tests/<package-path>/`
  * Example in this repository:
    `tika-parsers/tika-parsers-standard/tika-parsers-standard-modules/tika-parser-pdf-module/chatunitest-tests/org/apache/tika/parser/pdf/`
* **Output Artifacts:**
  * `<ClassName>_<methodName>_<testNum>_<round>_Test.java` (individual candidate tests).
  * `<ClassName>_Suite.java` (JUnit Platform test suite aggregating the generated classes).

> **Note:** Tests are **not** placed directly into the standard project test tree (`src/test/java`) during generation. They reside in `chatunitest-tests/` until moved via `mvn chatunitest:copy` or copied manually by the developer.

---

## 2. Compilation and Build Feasibility: Do Tests Compile Right Away?

**No, manual interventions are required.**

While ChatUniTest incorporates an internal compile-and-repair loop (querying the LLM up to `maxRounds = 3` to fix syntax errors reported by `javac`), the generated tests **do not** compile or pass the project build out of the box when integrated into Apache Tika.

---

## 3. Extent of Manual Interventions Needed

The required interventions fall into five distinct technical areas, which motivated establishing a codified mitigation workflow:

### A. Code Style & Linter Violations (Required for Every Test)
* **Problem:** ChatUniTest systematically injects wildcard / star imports:
  ```java
  import static org.junit.jupiter.api.Assertions.*;
  import static org.mockito.Mockito.*;
  import org.junit.jupiter.api.*;
  import org.mockito.*;
  ```
* **Impact:** Apache Tika enforces strict Maven Checkstyle rules with `AvoidStarImportCheck`. Any file containing wildcard imports causes `mvn checkstyle:check` and `mvn test` to fail immediately.
* **Manual Intervention:**
  * The developer must inspect the test and replace wildcard imports with explicit imports (e.g., `assertEquals`, `assertNotNull`, `Test`, `Mockito`).
  * Unused imports generated by ChatUniTest must be removed.

### B. Module & Build Configuration (One-Time per Module)
* **Problem (Missing Mockito Dependencies):** ChatUniTest frequently generates tests relying on Mockito (`Mockito.mock()`, `when()`, `any()`).
* **Impact:** If the module's `pom.xml` does not declare `mockito-core` and `mockito-junit-jupiter` in test scope, tests fail with `package org.mockito does not exist`.
* **Manual Intervention:** Add Mockito dependencies directly to the submodule's `pom.xml`.
* **Pre-packaging Requirement:** ChatUniTest requires the target module JAR to be present in `target/` before execution (`mvn package -DskipTests`).

### C. Build Directory Cleanup (Orphaned Test Classes)
* **Problem:** When ChatUniTest evaluates test candidates, it compiles them directly into `target/test-classes/`. If a candidate test fails assertions during generation (e.g., expected version `"1"` but actual was `"1.6"`), ChatUniTest discards the test and does not copy the `.java` file into `src/test/java`.
* **Impact:** The failing `.class` file remains in `target/test-classes/`. When the developer subsequently runs `mvn test`, Maven Surefire picks up and runs all `.class` files in `target/test-classes/`, causing the entire build to fail on an orphan class.
* **Manual Intervention:** The developer must clean or manually remove stray `.class` files from `target/test-classes/`.

### D. Assertion Accuracy and Semantic Verification
* **Problem (Hallucinated Assertions):** LLMs often make plausible but incorrect assumptions about internal APIs or return values. For example:
  * Asserting that a newly created PDF document has PDF version `"1"`, whereas PDFBox defaults to `"1.6"`.
  * Passing mocks where real context objects or stream caches are expected.
* **Manual Intervention:** A human developer must review the test logic, adjust erroneous expected values, and verify that the tests assert actual system behavior rather than hallucinated assumptions.

### E. Service Provider Interface (SPI) Metadata Regeneration (Tika-Specific)
* **Problem:** Apache Tika uses `@TikaComponent` annotation processing during `mvn compile` to generate `META-INF/services/` and `META-INF/tika/*.idx`.
* **Impact:** If the build directory is partially cleaned or overwritten, parser discovery fails at runtime (`Unknown component type: 'pdf-parser'` or fallback to `EmptyParser`).
* **Manual Intervention:** Re-run `mvn compile -pl <module>` to trigger annotation processing and regenerate SPI descriptor files.

### F. Workflow Mitigation: The `chatunitest-generator` Skill
Because ChatUniTest operates in isolation from project-wide linting and build standards, every test generation round predictably produces code that requires manual refinement (e.g., illegal star imports, missing test dependencies, orphaned test binaries, and fragile assertions). To prevent recurring developer friction and standardize the remediation process early on, we created the [`.agents/skills/chatunitest-generator/SKILL.md`](.agents/skills/chatunitest-generator/SKILL.md) skill. This skill encodes the systematic runbook needed to clean, reformat, compile, and validate ChatUniTest outputs to meet Apache Tika's strict engineering conventions.
